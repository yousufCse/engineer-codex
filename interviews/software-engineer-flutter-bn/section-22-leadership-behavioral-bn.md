> **Senior Flutter / Mobile Engineer — Interview Prep**

## এই Section কীভাবে ব্যবহার করবেন

প্রতিটা প্রশ্নের গঠন একই:

- **সংক্ষিপ্ত উত্তর (এটাই বলুন)** — ২–৩ বাক্যের উত্তর (বা framing), যেটা দিয়ে শুরু করবেন।
- **এবার পুরোটা বুঝি** — আপনার approach ধাপে ধাপে, অথবা নমুনা গল্প সহ STAR breakdown।
- **Interviewer কেন জিজ্ঞেস করে** · **সাধারণ ভুল** · **যে Follow-up প্রশ্ন আসতে পারে**
- **সম্পর্কিত** — সম্পর্কিত প্রশ্নে যান · **উপরে ফিরুন** — index-এ ফিরে যান।

প্রতিটা প্রশ্নে ট্যাগ দেওয়া আছে — কত ঘন ঘন জিজ্ঞেস করা হয় (**Very common / Common / Deeper**) আর কতটা কঠিন (**Easy / Medium / Hard**)।

> **Interview Tip:** Leadership প্রশ্নে শুধু নিয়ম নয়, *বিচারবুদ্ধি আর সহানুভূতি* দেখান। Behavioral প্রশ্নে **STAR** (নিচে) ব্যবহার করুন আর **সবসময় মাপা যায় এমন result দিয়ে শেষ করুন**। আর নিজের *সত্যিকারের গল্প* ব্যবহার করুন — এখানকার নমুনাগুলো template, নিজের অভিজ্ঞতা দিয়ে ভরে নিন।

**STAR method (প্রতিটা behavioral প্রশ্নের জন্য):**

| অক্ষর | মানে | যেভাবে রাখবেন... |
|---|---|---|
| **S — Situation** | প্রেক্ষাপট / পটভূমি | ছোট (১–২ বাক্য) |
| **T — Task** | আপনার নির্দিষ্ট লক্ষ্য / দায়িত্ব | স্পষ্ট |
| **A — Action** | **আপনি** যা করেছেন ("we" নয়, "I" ব্যবহার করুন) | সবচেয়ে বড় অংশ |
| **R — Result** | ফলাফল, **সংখ্যা** সহ | নির্দিষ্ট আর ইতিবাচক |

## <a id="q1"></a>1. আপনি কীভাবে code review করেন? কী কী খোঁজেন?

> Very common · Medium · [🇬🇧 English](../software-engineer-flutter/section-22-leadership-behavioral.md#q1)

**সংক্ষিপ্ত উত্তর (এটাই বলুন):**
"আমি স্তরে স্তরে review করি — আগে correctness আর design, তারপর readability। শুধু style-এর অংশটা linter-কে সামলাতে দিই। আমি edge case, স্পষ্ট naming, ভালো structure আর test খুঁজি। সমান গুরুত্বপূর্ণ হলো আমি *কীভাবে* feedback দিই: আদেশ না দিয়ে প্রশ্ন করি, ভদ্র আর নির্দিষ্ট থাকি, আর দ্রুত review করি যাতে team আটকে না যায়।"

**এবার পুরোটা বুঝি:**

**ধাপ ১ — কী কী খুঁজি, গুরুত্ব অনুযায়ী।**
1. **Correctness** — এটা কাজ করে তো, edge case সহ (null, খালি, error)?
2. **Design** — সঠিক জায়গায় আছে তো, structure ভালো তো, বেশি over-engineered নয় তো?
3. **Readability** — স্পষ্ট নাম, ছোট function, কোনো চমক নেই।
4. **Tests** — পরিবর্তনগুলো test দিয়ে ঢাকা আছে তো?
5. **Style** — formatter/linter-এর হাতে ছেড়ে দিন, খুঁটিনাটি নিয়ে ঘাঁটবেন না।

**ধাপ ২ — কীভাবে feedback দিই (সুরটাই সবচেয়ে বড়)।**
- **প্রশ্ন** করুন: "list খালি হলে এখানে কী হবে?" — "This is wrong."-এর চেয়ে অনেক ভালো।
- **নির্দিষ্ট আর ভদ্র** থাকুন — code নিয়ে কথা বলুন, মানুষ নিয়ে কখনোই না।
- **কারণটা ব্যাখ্যা করুন**, যাতে এটা শেখানোর সুযোগ হয়।
- **যথেষ্ট ভালো হলেই approve করুন**, নিখুঁত হওয়ার অপেক্ষা নয়; ছোট জিনিসগুলো optional হিসেবে চিহ্নিত করুন।

```dart
// "This is wrong." — এর বদলে
// আমি লিখি: "If getAll() throws, _loading stays true forever — wrap in try/finally?"
```

**ধাপ ৩ — Senior হিসেবে আমি review-কে শেখানোর কাজেও ব্যবহার করি।**
Review জ্ঞান আর standard ছড়িয়ে দেয়। আমি শুধু বলি না যে একটা pattern ভালো — *কেন* ভালো সেটাও দেখাই, যাতে লেখক শেখে।

**Interviewer কেন জিজ্ঞেস করে:** Code review একজন senior-এর প্রতিদিনের দায়িত্ব। তাঁরা আপনার বিচারবুদ্ধি আর মানুষের সাথে আচরণ যাচাই করেন।

**সাধারণ ভুল:** Linter যা সামলায় সেই style নিয়ে খুঁটিনাটি ধরা, অথচ আসল bug চোখ এড়িয়ে যাওয়া। অথবা কড়া বা অস্পষ্ট feedback দিয়ে মানুষের উৎসাহ নষ্ট করা।

**যে Follow-up প্রশ্ন আসতে পারে:**
- *"বিশাল বড় PR কীভাবে সামলান?"* → ভাগ করে দিতে বলুন; বড় PR-এ review সবসময় ভাসা-ভাসা হয়।

## <a id="q2"></a>2. আপনি junior বা mid-level developer-দের কীভাবে mentor করেন?

> Common · Medium · [🇬🇧 English](../software-engineer-flutter/section-22-leadership-behavioral.md#q2)

**সংক্ষিপ্ত উত্তর (এটাই বলুন):**
"তাঁরা এখন যেখানে আছেন, আমি সেখান থেকেই শুরু করি। তারপর ধীরে ধীরে তাঁদের স্বাধীনতা বাড়াই। আমি সমস্যায় pair করি, শুধু উত্তর না দিয়ে context আর 'কেন'টা দিই, ছোট ছোট stretch goal দিই, আর code review-কে শেখানোর সুযোগ হিসেবে ব্যবহার করি। লক্ষ্য হলো তাঁদের স্বাবলম্বী করা, আমার উপর নির্ভরশীল করা নয়।"

**এবার পুরোটা বুঝি:**

**ধাপ ১ — মানুষ অনুযায়ী মানিয়ে নিন।**
একজন junior-এর বেশি guidance আর আত্মবিশ্বাস দরকার। একজন mid-level-এর দরকার ownership আর চ্যালেঞ্জ। আমি প্রত্যেকের জন্য আলাদা করে সহায়তা সাজাই।

**ধাপ ২ — শুধু উত্তর নয়, 'কেন'টা শেখান।**
উত্তর দিয়ে দিলে আজকের সমস্যা মেটে। কারণটা বুঝিয়ে দিলে এমন একজন developer তৈরি হয়, যিনি পরেরটা একা সমাধান করেন। পারলে আমি প্রশ্ন করে করে তাঁদের উত্তরের দিকে নিয়ে যাই।

**ধাপ ৩ — Mentoring-এর বাস্তব কাজগুলো।**
- কঠিন সমস্যায় **pair programming**।
- **Code review** — নরমভাবে, ব্যাখ্যা সহ শেখানোর জন্য।
- **ছোট stretch goal** — তাঁদের comfort zone-এর একটু বাইরে, কিন্তু নিরাপত্তা জাল সহ।
- **নিয়মিত 1:1** — শুধু task নয়, বেড়ে ওঠা আর আটকে থাকা দূর করার জন্য।

**ধাপ ৪ — স্বাধীনতা আর আত্মবিশ্বাস গড়ুন।**
আমি তাঁদের (নিরাপদ) ভুল করতে দিই আর সেখান থেকে শিখতে দিই। অগ্রগতির প্রশংসা করি, আর ধীরে ধীরে আরও ownership হাতে তুলে দিই। সফলতা তখনই, যখন ওই কাজের জন্য তাঁদের আর আমাকে লাগে না।

**Interviewer কেন জিজ্ঞেস করে:** Senior engineer পুরো team-কে বড় করেন। Mentoring দেখায় আপনি শুধু নিজেকে নয়, অন্যদেরও গড়ে তোলেন।

**সাধারণ ভুল:** তাঁদের *হয়ে* কাজটা করে দেওয়া (দ্রুত হয়, কিন্তু তাঁরা শেখেন না)। অথবা context ছাড়া শুধু উত্তর ছুঁড়ে দেওয়া।

**যে Follow-up প্রশ্ন আসতে পারে:**
- *"একজন mentee একই ভুল বারবার করছেন?"* → মূল কারণ খুঁজুন (জ্ঞানের ঘাটতি? তাড়াহুড়ো?), approach বদলান, আর ধৈর্য রাখুন।

## <a id="q3"></a>3. Teammate বা architect-এর সাথে technical মতভেদ কীভাবে সামলান?

> Very common · Medium · [🇬🇧 English](../software-engineer-flutter/section-22-leadership-behavioral.md#q3)

**সংক্ষিপ্ত উত্তর (এটাই বলুন):**
"আমি সমস্যার দিকে মন দিই, জেতার দিকে নয়। আগে নিশ্চিত করি যে তাঁদের মতটা আমি বুঝেছি। তারপর প্রমাণ আর trade-off সহ নিজের মত রাখি, আর project-এর জন্য সবচেয়ে ভালো option খুঁজি। এরপরও মত না মিললে prototype করি বা data-কে সিদ্ধান্ত নিতে দিই। Team সিদ্ধান্ত নেওয়ার পর আমি পুরোপুরি সেটার পাশে থাকি — সেটা আমার পছন্দ না হলেও।"

**এবার পুরোটা বুঝি:**

**ধাপ ১ — রাজি করানোর আগে বুঝুন।**
প্রথমে তাঁদের অবস্থানটা আমি নিজের ভাষায় বলি, যাতে তাঁরা বোঝেন আমি ধরতে পেরেছি। অনেক সময় মতভেদ আসলে ভুল বোঝাবুঝি। অথবা তাঁদের কাছে এমন context আছে যা আমার নেই।

**ধাপ ২ — ego নয়, প্রমাণ দিয়ে যুক্তি দিন।**
মতামত নয়, trade-off তুলে ধরুন: "Option A সহজ, কিন্তু X-এর বেশি scale করবে না; option B-তে কাজ বেশি, কিন্তু বৃদ্ধি সামলাতে পারবে।" পুরো আলোচনাটা project-এর প্রয়োজন নিয়ে রাখুন।

**ধাপ ৩ — গঠনমূলকভাবে সমাধান করুন।**
- **Prototype/spike** করে data-কে সিদ্ধান্ত নিতে দিন ([Q15 SDLC](section-19-sdlc-bn.md#q15))।
- আটকে গেলে **তৃতীয় একজনের মত** নিন।
- **Disagree and commit** — team সিদ্ধান্ত নেওয়ার পর আমি পুরোপুরি সেটাকে সমর্থন করি, সেটা আমার মত না হলেও।

**ধাপ ৪ — সম্পর্কটা ভালো রাখুন।**
লক্ষ্য হলো সেরা ফলাফল, *আর সাথে* ভালো কাজের সম্পর্ক। আমি কখনোই এটাকে ব্যক্তিগত করি না; আজকের "প্রতিপক্ষ" আগামীকালের সহযোগী।

**Interviewer কেন জিজ্ঞেস করে:** মতভেদ সবসময় হবেই। তাঁরা দেখতে চান আপনি এটা পরিণতভাবে সামলান কি না, আর সহযোগী থাকেন কি না।

**সাধারণ ভুল:** এটাকে ego-র লড়াই বানিয়ে ফেলা। অথবা team সিদ্ধান্ত নেওয়ার পরও সেটা মেনে না নেওয়া ("আমি তো আগেই বলেছিলাম" ভাব)।

**যে Follow-up প্রশ্ন আসতে পারে:**
- *"আপনার মত বাতিল হলো, কিন্তু আপনি মনে করেন সিদ্ধান্তটা ভুল?"* → ঝুঁকিটা স্পষ্ট করে জানান (দরকারে লিখিতভাবে), তারপর মেনে নিন আর কাজটা সফল করতে সাহায্য করুন; সমস্যা দেখা দিলে data নিয়ে আবার আলোচনা করুন।

## <a id="q4"></a>4. আপনি team-এ নতুন library বা technology কীভাবে introduce করেন?

> Common · Medium · [🇬🇧 English](../software-engineer-flutter/section-22-leadership-behavioral.md#q4)

**সংক্ষিপ্ত উত্তর (এটাই বলুন):**
"সাবধানে, আর প্রমাণসহ। আমি প্রথমে নিশ্চিত করি যে এটা সত্যিকারের একটা সমস্যা সমাধান করে। তারপর option-গুলো যাচাই করি (maturity, maintenance, community, fit)। এরপর ছোট একটা spike বা proof-of-concept চালাই, আর ফলাফল team-এর সাথে share করি। adopt করার আগে আমি buy-in নিই। আর সব একসাথে rewrite না করে ধাপে ধাপে roll out করি।"

**এবার পুরোটা বুঝি:**

**ধাপ ১ — চকচকে tool নয়, সমস্যা দিয়ে শুরু করুন।**
নতুন tech-কে সত্যিকারের একটা কষ্ট দূর করতে হবে। "এটা এখন trendy" — এটা কোনো কারণ নয়। আমি আগে সমস্যাটার নাম বলি।

**ধাপ ২ — ঠিকভাবে যাচাই করুন।**
- **Maturity & maintenance** — এটা কি সক্রিয়ভাবে maintain হয়, ব্যাপকভাবে ব্যবহৃত, stable?
- **Fit** — এটা কি আমাদের app আর team-এর skill-এর সাথে মানায়?
- **Cost** — শেখার খরচ, migration-এর পরিশ্রম, lock-in ঝুঁকি।
- **Alternatives** — "কিছুই না করা" বা আমাদের হাতে যা আছে তা ব্যবহার করাও এর মধ্যে পড়ে।

**ধাপ ৩ — spike দিয়ে প্রমাণ করুন।**
ছোট একটা proof-of-concept সিদ্ধান্তের ঝুঁকি কমায় ([Q15 SDLC](section-19-sdlc-bn.md#q15))। এটা মতামতের বদলে বাস্তব প্রমাণ দেয়।

**ধাপ ৪ — buy-in নিন, আর ধাপে ধাপে roll out করুন।**
ফলাফল share করুন, team হিসেবে আলোচনা করুন, আর অল্প অল্প করে adopt করুন (প্রথমে একটা feature)। big-bang rewrite নয়। সিদ্ধান্তটা document করুন ([Q7](#q7)) আর team-কে শিখতে সাহায্য করুন।

**Interviewer কেন জিজ্ঞেস করে:** এটা যাচাই করে আপনি hype-এর পিছনে ছোটেন, নাকি ভারসাম্যপূর্ণ ও team-সচেতন technology সিদ্ধান্ত নেন।

**সাধারণ ভুল:** buy-in বা সত্যিকারের প্রয়োজন ছাড়াই একা একা trendy tech নিয়ে আসা, তারপর একটা ঝুঁকিপূর্ণ big-bang migration চাপিয়ে দেওয়া।

**যে Follow-up প্রশ্ন আসতে পারে:**
- *"একজন junior একটা ঝকঝকে নতুন state-management library যোগ করতে চায় — আপনি কী বলবেন?"* → উদ্যোগটাকে স্বাগত জানান, তারপর একসাথে সত্যিকারের প্রয়োজন আর team-এর consistency-র সাথে মিলিয়ে যাচাই করুন।

## <a id="q5"></a>5. Technical debt আপনি কীভাবে manage করেন আর শোধ করেন?

> Common · Medium · [🇬🇧 English](../software-engineer-flutter/section-22-leadership-behavioral.md#q5)

**সংক্ষিপ্ত উত্তর (এটাই বলুন):**
"আমি এটাকে দৃশ্যমান করি, আর ধীরে ধীরে শোধ করি। উপেক্ষাও করি না, বড় rewrite-ও দাবি করি না। আমি debt item-গুলো backlog-এ track করি, আর সেগুলোকে business impact-এর সাথে জুড়ে দিই (bug, ধীর delivery)। প্রতিটা sprint-এর একটা অংশ সবচেয়ে খারাপ debt-এর জন্য রাখি। আর review আর শক্ত Definition of Done দিয়ে নতুন debt আটকাই।"

**এবার পুরোটা বুঝি:**

**ধাপ ১ — এটাকে দৃশ্যমান করুন।**
মানুষের মাথায় রাখা debt কখনোই ঠিক হয় না। আমি debt item-গুলো তাদের impact সহ backlog-এ log করি। ফলে সেগুলো বাস্তব ও prioritize করার মতো কাজ হয়ে যায়।

**ধাপ ২ — Business impact দেখে prioritize করুন।**
সব debt সমান নয়। আমি সেই debt-এ মন দিই যেটা সবচেয়ে বেশি bug তৈরি করে, বা সবচেয়ে বেশি বদলানো অংশকে ধীর করে। আর এটাকে business-এর ভাষায় বলি: "এই module আমাদের 40% bug-এর কারণ।"

**ধাপ ৩ — ধীরে ধীরে শোধ করুন।**
- **Budget** — প্রতিটা sprint-এর ~10–20% debt-এর জন্য।
- **Boy scout rule** — আপনি যে code ইতিমধ্যে ছুঁচ্ছেন, তার আশপাশটা একটু ভালো করে দিন।
- **Big-bang rewrite এড়ান** — ঝুঁকিপূর্ণ, আর সাধারণত reject হয়; ধাপে ধাপে করাই ভালো (বড় ক্ষেত্রে Strangler Fig)।

**ধাপ ৪ — নতুন debt আটকান।**
Code review, শক্ত Definition of Done, test, আর পরিষ্কার standard — এগুলো স্তূপটাকে বড় হতে দেয় না।

**Interviewer কেন জিজ্ঞেস করে:** Debt-এ ভারসাম্য রাখা senior judgment-এর মূল অংশ — উপেক্ষাও নয়, আবার অতিরিক্ত মাথাব্যথাও নয়।

**সাধারণ ভুল:** Codebase অচল হয়ে যাওয়া পর্যন্ত debt উপেক্ষা করা। অথবা বলা — "refactor করার জন্য এক মাস feature বন্ধ রাখুন" (stakeholder-দের ভয় পাইয়ে দেয়, ঝুঁকিও বেশি)।

**যে Follow-up প্রশ্ন আসতে পারে:**
- *"PO-কে সময় বরাদ্দ করাতে কীভাবে রাজি করাবেন?"* → bug rate আর ধীর delivery-তে খরচটা দেখান; ছোট একটা নিয়মিত budget প্রস্তাব করুন।

## <a id="q6"></a>6. Delivery-র গতি আর code quality-র মধ্যে ভারসাম্য কীভাবে রাখেন?

> Very common · Medium · [🇬🇧 English](../software-engineer-flutter/section-22-leadership-behavioral.md#q6)

**সংক্ষিপ্ত উত্তর (এটাই বলুন):**
"আমি এটাকে একটা সচেতন trade-off হিসেবে দেখি, কোনো নির্দিষ্ট নিয়ম হিসেবে নয়। দ্রুত একটা experiment বা deadline-এর ক্ষেত্রে আমি *সচেতনভাবে* shortcut নিই, আর পরে ঠিক করার জন্য সেটাকে debt হিসেবে log করি। মূল, দীর্ঘদিন টিকে থাকা code-এ quality জেতে, কারণ সময়ের সাথে সেটাই সস্তা। মূল কথা — সিদ্ধান্তটা সচেতনভাবে নেওয়া আর জানিয়ে দেওয়া। quality যেন চুপচাপ পড়ে না যায়।"

**এবার পুরোটা বুঝি:**

**ধাপ ১ — এটা context-এর উপর নির্ভর করে।**
- **ফেলে দেওয়ার মতো / experiment / জরুরি deadline** → গতি জিততে পারে; একটা *track করা* shortcut নিন।
- **মূল, দীর্ঘস্থায়ী, বেশি ঝুঁকির code** → quality জেতে; এখানে তাড়াহুড়ো করলে পরে অনেক বেশি খরচ হয়।

**ধাপ ২ — Shortcut-গুলো সচেতন আর দৃশ্যমান রাখুন।**
গতির জন্য আমি কোনো কোণা কাটলে সেটা বলে দিই, আর tech debt হিসেবে log করি ([Q5](#q5)) — ঠিক করার একটা পরিকল্পনাসহ। বিপদ shortcut-এ নয় — বিপদ সেই *চুপচাপ* shortcut-এ, যেটা কেউ track করে না।

**ধাপ ৩ — Quality নিজেই প্রায়ই গতি।**
বাস্তব যেকোনো সময়সীমায় পরিষ্কার, test করা code *দ্রুততর* — কম bug, সহজে বদলানো যায়। তাই "quality বনাম গতি" প্রায়ই একটা মিথ্যা পছন্দ; quality কমালে কয়েক সপ্তাহের মধ্যেই আপনি ধীর হয়ে যান।

**ধাপ ৪ — Trade-off-টা জানিয়ে দিন।**
আমি PO/team-এর কাছে খরচটা পরিষ্কার করি: "আমরা একটা জানা সীমাবদ্ধতা নিয়ে শুক্রবার ship করতে পারি, অথবা সোমবার ঠিকভাবে শেষ করে ship করতে পারি।" পুরো তথ্য নিয়ে business-কেই বেছে নিতে দিন।

**Interviewer কেন জিজ্ঞেস করে:** এই টানাপোড়েন সবসময় থাকে; তাঁরা গোঁড়ামি নয়, পরিণত ও সচেতন judgment দেখতে চান।

**সাধারণ ভুল:** সবসময় একটা চরম দিক বেছে নেওয়া — প্রতিবারই দ্রুত আবর্জনা ship করা, অথবা সব কিছুতে অতিরিক্ত পালিশ করে deadline মিস করা।

**যে Follow-up প্রশ্ন আসতে পারে:**
- *"Deadline-এর চাপে shortcut নিতেই হচ্ছে — আপনি কী করবেন?"* → সচেতনভাবে নিন, debt-টা document করুন, আর ঠিক করার সময় নির্ধারণ করুন; কখনোই লুকাবেন না।

## <a id="q7"></a>7. আপনি architectural সিদ্ধান্ত কীভাবে নেন, আর সেগুলো কীভাবে document করেন?

> Common · Medium · [🇬🇧 English](../software-engineer-flutter/section-22-leadership-behavioral.md#q7)

**সংক্ষিপ্ত উত্তর (এটাই বলুন):**
"আমি requirement আর constraint সংগ্রহ করি। তারপর কয়েকটা বাস্তবসম্মত option তাদের trade-off সহ তালিকা করি। এরপর project-এর আসল প্রয়োজন দেখে বেছে নিই — সবচেয়ে trendy option দেখে নয়। গুরুত্বপূর্ণ সিদ্ধান্তগুলো আমি ছোট ADR (Architecture Decision Record) হিসেবে document করি। সেখানে থাকে context, option-গুলো, কোনটা বেছে নেওয়া হলো, আর *কেন*। ফলে ভবিষ্যতের developer-রা যুক্তিটা বুঝতে পারেন।"

**এবার পুরোটা বুঝি:**

**ধাপ ১ — আসল প্রয়োজন দেখে সিদ্ধান্ত নিন।**
Requirement দিয়ে শুরু করুন (scale, team-এর আকার, আয়ু, constraint)। architecture-কে *সেগুলোর* সাথে মেলান, আপনি যে pattern ব্যবহার করতে চান তার সাথে নয় ([Q14 Architecture](section-13-architecture-patterns-bn.md#q14))।

**ধাপ ২ — Option আর trade-off তুলনা করুন।**
২–৩টি বাস্তবসম্মত option তালিকা করুন, প্রতিটির সুবিধা/অসুবিধা সহ। একটাই "সঠিক" উত্তর খুব কমই থাকে — থাকে এই context-এর জন্য সবচেয়ে মানানসই উত্তর। buy-in-এর জন্য team-কে সাথে রাখুন।

**ধাপ ৩ — ADR দিয়ে document করুন।**
প্রতিটা গুরুত্বপূর্ণ সিদ্ধান্তের জন্য একটা ছোট record:

```
# ADR: State management choice
Context:  large app, 8 devs, need testability
Options:  Provider, Riverpod, BLoC
Decision: BLoC — team knows it, testable, event-traceable
Why:      consistency + testability outweigh extra boilerplate
```

**ধাপ ৪ — 'কেন' লেখা কেন দরকার।**
ছয় মাস পরে কেউ জিজ্ঞেস করবে "আমরা এটা কেন করেছিলাম?" ADR না থাকলে সেই জ্ঞান হারিয়ে যায়। তখন মানুষ সন্দেহ করে বা সিদ্ধান্ত ভেঙে ফেলে। ADR খুব কম খরচে যুক্তিটা ধরে রাখে।

**Interviewer কেন জিজ্ঞেস করে:** এটা গোছানো সিদ্ধান্ত নেওয়া আর যোগাযোগ যাচাই করে — senior/lead ভূমিকার জন্য এটা মূল জিনিস।

**সাধারণ ভুল:** কোনো documented যুক্তি ছাড়া একা সিদ্ধান্ত নেওয়া (ফলে সেটা হারিয়ে যায়)। অথবা মানানসই কি না না দেখে hype দেখে tech বেছে নেওয়া।

**যে Follow-up প্রশ্ন আসতে পারে:**
- *"ADR জিনিসটা কী?"* → একটা সিদ্ধান্ত, option-গুলো আর যুক্তির ছোট, হালকা doc — code-এর সাথেই রাখা হয়।

## <a id="q8"></a>8. বড় একটা Flutter codebase-এ নতুন developer-কে কীভাবে onboard করেন?

> Common · Medium · [🇬🇧 English](../software-engineer-flutter/section-22-leadership-behavioral.md#q8)

**সংক্ষিপ্ত উত্তর (এটাই বলুন):**
"প্রথম সপ্তাহটা আমি ছোট ছোট জয় আর context নিয়ে সাজাই, পুরো codebase একসাথে নয়। আমি নিশ্চিত করি setup doc কাজ করে, তাড়াতাড়ি একটা ছোট আসল কাজ দিই, আর একজন buddy-র সাথে জুড়ে দিই। architecture আর convention ঘুরে দেখাই, আর তাঁর প্রথম feature-এর জন্য যে অংশগুলো দরকার সেগুলো দেখিয়ে দিই। লক্ষ্য হলো — দ্রুত একটা আত্মবিশ্বাসী প্রথম PR।"

**এবার পুরোটা বুঝি:**

**ধাপ ১ — তাঁকে দ্রুত productive করুন।**
একটা পরিষ্কার, কাজ করা **setup guide** (এক ঘণ্টার কমে app চলবে) আর প্রথম সপ্তাহে একটা **ছোট starter task** — এই দুটো শুরুতেই জয় আর আত্মবিশ্বাস দেয়।

**ধাপ ২ — Context দিন, তথ্যের বন্যা নয়।**
তাঁকে **বড় ছবিটা** ঘুরে দেখান: architecture, folder structure, মূল pattern, আর কীভাবে run/test করতে হয়। প্রতিটা খুঁটিনাটি তাঁর লাগবে না — লাগবে একটা map আর কোথায় খুঁজতে হবে সেটা।

**ধাপ ৩ — একজন buddy-র সাথে জুড়ে দিন।**
"বোকা প্রশ্ন" করার জন্য একজন নির্দিষ্ট মানুষ থাকলে ভয় কেটে যায়। এটা একা doc পড়ার চেয়ে অনেক দ্রুত শেখায়।

**ধাপ ৪ — ফাঁকগুলো document করুন।**
Onboarding-এ যদি doc-এর ঘাটতি বা গোলমাল ধরা পড়ে, সেগুলো ঠিক করুন — এতে পরের জনের onboarding ভালো হয় (আর নতুন hire-এর জন্য এটা দারুণ একটা starter task)।

**Interviewer কেন জিজ্ঞেস করে:** ভালো onboarding দেখায় আপনি team-কে বড় করেন, আর অন্যের ramp-up-কে মূল্য দেন — শুধু নিজের output নয়।

**সাধারণ ভুল:** কোনো দিকনির্দেশনা ছাড়াই তাঁকে বিশাল জটিল একটা feature-এ ফেলে দেওয়া। অথবা code ছোঁয়ার আগে সব কিছু পড়তে বলা (ধীর, আর মনোবল ভেঙে দেয়)।

**যে Follow-up প্রশ্ন আসতে পারে:**
- *"নতুন একজন senior-এর প্রথম কাজ কী?"* → আসল কিন্তু সীমিত কিছু, যেটা কয়েকটা অংশ ছুঁয়ে যায়, সাথে একজন buddy — যাতে করতে করতেই তিনি system-টা শেখেন।

## <a id="q9"></a>9. আপনার চেয়ে বেশি senior একজন developer-এর PR আপনি কীভাবে review করেন?

> Common · Medium · [🇬🇧 English](../software-engineer-flutter/section-22-leadership-behavioral.md#q9)

**সংক্ষিপ্ত উত্তর (এটাই বলুন):**
"সবার জন্য একই standard — আমি যত্ন নিয়ে আর সৎভাবে review করি। 'ভুলটা আমারই' — এটা ধরে না নিয়ে আমি তাঁর যুক্তি বোঝার জন্য প্রশ্ন করি। উদ্বেগগুলো সম্মানের সাথে, প্রমাণসহ তুলি। আর তাঁর approach থেকে শিখতেও আমি খোলা থাকি। ভালো senior-রা সত্যিকারের review *চান*, rubber stamp নয়।"

**এবার পুরোটা বুঝি:**

**ধাপ ১ — ভয়ে পড়ে rubber-stamp করবেন না।**
Senior-রাও ভুল করেন, আর তাঁরা আসল review-কে মূল্য দেন। শুধু পদবি দেখে চোখ বুজে approve করলে কারো লাভ হয় না। এতে review-এর উদ্দেশ্যই নষ্ট হয়।

**ধাপ ২ — অভিযোগ নয়, প্রশ্ন করুন।**
উদ্বেগগুলো প্রশ্ন হিসেবে সাজান: "হয়তো আমি context মিস করছি — response null হলে এখানে কী হবে?" এটা সম্মানজনক। আর এতে প্রায়ই হয় একটা সত্যিকারের সমস্যা বেরিয়ে আসে, নয়তো আমার জন্য দরকারি context।

**ধাপ ৩ — প্রমাণ আনুন, বিনয়ী থাকুন।**
কোনো সমস্যা চোখে পড়লে আমি যুক্তি বা একটা doc/standard দিয়ে সেটা সমর্থন করি। আর আমি খোলা থাকি — কখনো কখনো তাঁর approach-ই ঠিক, আর আমি কিছু শিখি। এটা দুই দিকের আলোচনা।

**ধাপ ৪ — বিষয়টা code নিয়ে, পদমর্যাদা নিয়ে নয়।**
সুস্থ team সবার code সমানভাবে review করে। এটা ভালোভাবে করলে আত্মবিশ্বাসও দেখা যায়, আর সম্মানও অর্জিত হয়।

**Interviewer কেন জিজ্ঞেস করে:** এটা আত্মবিশ্বাস, বিনয়, আর hierarchy নির্বিশেষে standard ধরে রাখা যাচাই করে।

**সাধারণ ভুল:** সত্যিকারের review ছাড়াই senior-এর PR অটো-approve করা। অথবা উল্টোটা — নিজের কথা প্রমাণ করতে ঝগড়াটে হয়ে যাওয়া।

**যে Follow-up প্রশ্ন আসতে পারে:**
- *"তিনি আপনার comment উড়িয়ে দিলেন — এখন কী?"* → trade-off নিয়ে শান্তভাবে আলোচনা করুন; বিষয়টা গুরুত্বপূর্ণ হলে data বা তৃতীয় একজনের মতামত আনুন; ছোট হলে ছেড়ে দিন।

**সম্পর্কিত:** [Q1 — code review](#q1) · [Q3 — মতভেদ](#q3)

# B. Behavioral (STAR)

> **STAR** পদ্ধতি ব্যবহার করুন (এই section-এর শুরুতে দেওয়া আছে)। নিজের অভিজ্ঞতা থেকে ৩–৪টি *সত্যিকারের* গল্প তৈরি রাখুন। এগুলো ঘুরিয়ে-ফিরিয়ে অনেক প্রশ্নের সাথে মেলানো যায়। নিচের নমুনাগুলো template মাত্র — নিজের project আর নিজের সংখ্যা দিয়ে বদলে নিন।

## <a id="q10"></a>10. নিজের সম্পর্কে বলুন (senior-level framing)।

> Very common · Easy–Medium · [🇬🇧 English](../software-engineer-flutter/section-22-leadership-behavioral.md#q10)

**সংক্ষিপ্ত উত্তর (এটাই বলুন):**
"এটা ~৯০ সেকেন্ডে তিন ভাগে রাখুন: আপনি কে তার এক লাইনের সারসংক্ষেপ, role-এর সাথে মেলে এমন ২–৩টি highlight (impact সহ), আর কেন *এই* কাজটা নিয়ে আপনি উৎসাহী। এটা একটা pitch, জীবনকাহিনি নয় — senior Flutter role-এর জন্য যা সবচেয়ে প্রাসঙ্গিক, সেটা দিয়ে শুরু করুন।"

**এবার পুরোটা বুঝি:**

**ধাপ ১ — ৩ ভাগের structure।**
1. **Present** — "আমি একজন senior Flutter engineer, ~৬ বছর ধরে production mobile app বানাচ্ছি।"
2. **Highlights** — role-এর সাথে মেলে এমন ২–৩টি অর্জন, impact সহ: "আমি আমাদের e-commerce app-কে Clean Architecture + BLoC-এ rewrite করার নেতৃত্ব দিয়েছি। এতে crash rate 60% কমেছে, আর নতুন dev-দের onboarding সময় অর্ধেক হয়েছে।"
3. **Why this role** — "এই role-টা আমাকে টানছে কারণ [company/product নিয়ে নির্দিষ্ট কারণ]।"

**ধাপ ২ — কাজটার সাথে মিলিয়ে নিন।**
Job description-এর সাথে মেলে এমন highlight বেছে নিন। Fintech role-এ apply করছেন? তাহলে security আর reliability-র উপর জোর দিন। Startup? তাহলে ownership আর দ্রুত ship করার উপর জোর দিন।

**ধাপ ৩ — কাজের তালিকা নয়, impact দিয়ে শুরু করুন।**
"আমি Flutter code লিখেছি" নয়। বরং "আমি app startup 40% ভালো করেছি এবং ৩ জন junior-কে স্বাধীনভাবে কাজ করার জায়গায় নিয়ে গেছি।" Senior মানে impact আর leadership, শুধু coding নয়।

**ধাপ ৪ — ছোট রাখুন (~৯০ সেকেন্ড)।**
Role নিয়ে উৎসাহ দেখিয়ে শেষ করুন। এতে কথা স্বাভাবিকভাবেই interviewer-এর হাতে ফিরে যায়।

**Interviewer কেন জিজ্ঞেস করে:** এটা পুরো interview-র সুর ঠিক করে দেয়। আর দেখায় আপনি পরিষ্কারভাবে কথা বলতে পারেন কি না, নিজেকে senior level-এ বসাতে পারেন কি না।

**সাধারণ ভুল:** পুরো ইতিহাস বলে যাওয়া, impact-এর বদলে কাজের তালিকা দেওয়া, বা role-এর সাথে না মিলিয়ে একটা সাধারণ pitch দেওয়া।

**যে Follow-up প্রশ্ন আসতে পারে:**
- *"ওই rewrite নিয়ে আরও একটু বলুন।"* → একটা STAR গল্প তৈরি রাখুন ([Q12](#q12))।

**সম্পর্কিত:** [Q18 — কেন এই role](#q18) · [Q11 — অর্জন](#q11)

## <a id="q11"></a>11. আপনার সবচেয়ে বড় technical achievement কী?

> Very common · Medium · [🇬🇧 English](../software-engineer-flutter/section-22-leadership-behavioral.md#q11)

**সংক্ষিপ্ত উত্তর (এটাই বলুন):**
"সত্যিকারের impact আছে এমন একটা অর্জন বেছে নিন এবং STAR-এ বলুন। ফলাফল দিয়ে শুরু করুন, তারপর চ্যালেঞ্জটা আর *আপনি* ঠিক কী করেছিলেন সেটা বলুন। এমন কিছু বাছুন যা senior গুণ দেখায় — কঠিন সমস্যার সমাধান, নেতৃত্ব, বা মাপা যায় এমন business value দেওয়া।"

**এবার পুরোটা বুঝি (STAR নমুনা — নিজের মতো করে বদলে নিন):**

- **Situation:** "আমাদের Flutter app-এর cold start ছিল ৩ সেকেন্ড আর crash rate ছিল 4%। User-রা অভিযোগ করছিলেন, review নামতে শুরু করেছিল।"
- **Task:** "team-এর senior হিসেবে বড় একটা marketing launch-এর আগে performance আর stability ঠিক করার দায়িত্ব আমার ছিল।"
- **Action:** "আমি DevTools দিয়ে profile করলাম, ভারী JSON parsing isolate-এ সরালাম, `const` widget আর লম্বা list-এর জন্য `ListView.builder` যোগ করলাম, leak তৈরি করা কয়েকটা uncancelled stream subscription ঠিক করলাম, আর alerting সহ Crashlytics বসালাম। দুই জন junior-এর সাথে pair-ও করেছি, যাতে তাঁরা এটা maintain করতে পারেন।"
- **Result:** "Cold start 3s থেকে 1.1s-এ নামল, crash-free user 96% থেকে 99.6% হলো, আর দুই মাসে app rating 3.8 থেকে 4.5-এ উঠল।"

**পরামর্শ:**
- **ফলাফল দিয়ে শুরু করুন**, যদি impact আগে দেখাতে চান। তারপর S-T-A ভরে দিন।
- নিজের কাজের জন্য **"আমি"** বলুন (interviewer *আপনাকে* নিয়োগ দিচ্ছেন)।
- **সংখ্যা** রাখুন — এতে গল্পটা বাস্তব আর senior শোনায়।

**Interviewer কেন জিজ্ঞেস করে:** এটা দেখায় আপনি কোনটাকে impactful মনে করেন। আর আপনি সেটা করতে ও বোঝাতে পারেন কি না, সেটাও দেখায়।

**সাধারণ ভুল:** মাপা যায় এমন ফলাফল ছাড়া অস্পষ্ট গল্প। বা এত বেশি "আমরা" বলা যে *আপনি* ঠিক কী করেছেন তা বোঝা যায় না।

**যে Follow-up প্রশ্ন আসতে পারে:**
- *"সবচেয়ে কঠিন অংশটা কী ছিল?"* → একটা নির্দিষ্ট technical চ্যালেঞ্জ আর তার সমাধান তৈরি রাখুন।

**সম্পর্কিত:** [Q15 — performance ভালো করা](#q15) · [Q12 — project lead করা](#q12)

## <a id="q12"></a>12. এমন একটা সময়ের কথা বলুন যখন আপনি শূন্য থেকে production পর্যন্ত একটা project lead করেছেন।

> Common · Medium · [🇬🇧 English](../software-engineer-flutter/section-22-leadership-behavioral.md#q12)

**সংক্ষিপ্ত উত্তর (এটাই বলুন):**
"STAR ব্যবহার করুন এবং *leadership* আর *delivery*-র উপর জোর দিন: আপনি কীভাবে scope ঠিক করলেন, মূল সিদ্ধান্ত নিলেন, মানুষজনকে সমন্বয় করলেন, সমস্যা সামলালেন, আর ফলাফল সহ ship করলেন। এটা শুরু থেকে শেষ পর্যন্ত ownership দেখানোর সুযোগ, শুধু coding নয়।"

**এবার পুরোটা বুঝি (STAR নমুনা — নিজের মতো বদলে নিন):**

- **Situation:** "আমাদের telemedicine Flutter app-এ কোম্পানির একটা নতুন patient-booking feature দরকার ছিল। আগে থেকে কোনো ভিত্তি ছিল না।"
- **Task:** "আমি শুরু থেকে শেষ পর্যন্ত এটা lead করেছি — architecture, ৩ জনের একটা team, আর ১০ সপ্তাহে delivery।"
- **Action:** "PO-র সাথে বসে requirement সংগ্রহ করলাম, Clean Architecture + BLoC বেছে নিলাম এবং একটা ADR-এ লিখে রাখলাম, কাজটা sprint-এ ভাগ করলাম, planning আর review চালালাম, কঠিন অংশে pair করলাম। মাঝপথে একটা API পরিবর্তন এলে সেটা repository-র পেছনে আলাদা করে রাখলাম, যাতে UI বারবার বদলাতে না হয়।"
- **Result:** "আমরা সময়মতো ship করেছি। Booking completion 25% বাড়ল, আর modular structure-এর কারণে পরের একটা feature-এ 60% কাজ পুনরায় ব্যবহার করতে পেরেছি।"

**পরামর্শ:**
- আপনি যে **সিদ্ধান্ত আর trade-off** নিয়েছেন সেগুলো দেখান (এটাই leadership)।
- আপনি কীভাবে **একটা সমস্যা সামলেছেন** সেটা বলুন (scope পরিবর্তন, blocker) — কোনো project-ই নিখুঁতভাবে চলে না।
- শুধু "ship হয়েছে" নয়, **business impact** দিয়ে শেষ করুন।

**Interviewer কেন জিজ্ঞেস করে:** এটা বাস্তব সীমাবদ্ধতার মধ্যে শুরু-থেকে-শেষ ownership আর leadership যাচাই করে।

**সাধারণ ভুল:** শুধু coding-এর কথা বলা আর leadership বাদ দেওয়া (planning, সিদ্ধান্ত, সমন্বয়, সমস্যা সামলানো)।

**যে Follow-up প্রশ্ন আসতে পারে:**
- *"এখন করলে কী আলাদা করতেন?"* → চিন্তাভাবনা দেখান — একটা সৎ উন্নতির কথা বলুন।

**সম্পর্কিত:** [Q11 — অর্জন](#q11) · [Q7 — architecture সিদ্ধান্ত](#q7)

## <a id="q13"></a>13. এমন একটা সময়ের কথা বলুন যখন আপনি একটা critical production bug ঠিক করেছেন।

> Very common · Medium · [🇬🇧 English](../software-engineer-flutter/section-22-leadership-behavioral.md#q13)

**সংক্ষিপ্ত উত্তর (এটাই বলুন):**
"STAR ব্যবহার করুন এবং চাপের মধ্যে শান্ত, নিয়মমাফিক প্রক্রিয়া দেখান: আগে impact আটকান, তারপর root cause খুঁজুন, একটা test সহ fix করুন যাতে সমস্যা ফিরে না আসে, নিরাপদে deploy করুন, আর blameless post-mortem করুন। Interviewer বীরত্ব চান না — তাঁরা ঠান্ডা মাথা আর process দেখতে চান।"

**এবার পুরোটা বুঝি (STAR নমুনা — নিজের মতো বদলে নিন):**

- **Situation:** "একটা release-এর পর আমাদের app প্রায় 30% Android user-এর login-এ crash করতে শুরু করল — একটা P0 incident।"
- **Task:** "আমি response lead করেছি এবং দ্রুত service ফেরানো দরকার ছিল।"
- **Action:** "প্রথমে আমি সমস্যা আটকালাম — ২০ মিনিটের মধ্যে release rollback করলাম, যাতে user-রা login করতে পারেন। তারপর Crashlytics থেকে সেটা reproduce করলাম। দেখলাম, বদলে যাওয়া API response থেকে একটা null token আসছে যেটা আমরা handle করছিলাম না। একটা fix লিখলাম, সাথে crash reproduce করে এমন একটা test, আর hotfix দিয়ে deploy করলাম। এরপর একটা blameless post-mortem চালালাম এবং API-র বিরুদ্ধে একটা contract test যোগ করলাম।"
- **Result:** "Downtime ~২৫ মিনিটে সীমাবদ্ধ থাকল, কোনো data loss হয়নি। আর ওই contract test এরপর একই ধরনের দুটো সমস্যা ধরে ফেলেছে।"

**পরামর্শ:**
- **'আগে আটকান, root cause পরে'** — এটার উপর জোর দিন ([Q9 SDLC](section-19-sdlc-bn.md#q9))।
- যে **test** সমস্যাটা আবার আসা ঠেকায়, সেটার কথা বলুন।
- **Blameless** সুর রাখুন — কোনো মানুষকে দোষ না দিয়ে system-এর দিকে মনোযোগ দিন।

**Interviewer কেন জিজ্ঞেস করে:** এটা যাচাই করে আপনি চাপের মধ্যে কেমন আচরণ করেন। আর আপনি শুধু লক্ষণ নয়, কারণ ঠিক করেন কি না।

**সাধারণ ভুল:** "আমি ভয় পেয়ে গিয়েছিলাম আর কোনোমতে একটা fix বসিয়ে দিয়েছিলাম" — এমন এলোমেলো গল্প বলা। বা প্রতিরোধ ছাড়া শুধু লক্ষণ ঠিক করা।

**যে Follow-up প্রশ্ন আসতে পারে:**
- *"এটা আবার হওয়া কীভাবে ঠেকিয়েছেন?"* → test + একটা process/monitoring উন্নতি।

**সম্পর্কিত:** [Q9 (SDLC) — production bug](section-19-sdlc-bn.md#q9) · [Q19 (Git) — hotfix](section-17-git-bn.md#q19)

## <a id="q14"></a>14. এমন একটা সময়ের কথা বলুন যখন আপনার manager-এর সাথে আপনার মতের অমিল হয়েছিল।

> Very common · Medium · [🇬🇧 English](../software-engineer-flutter/section-22-leadership-behavioral.md#q14)

**সংক্ষিপ্ত উত্তর (এটাই বলুন):**
"STAR ব্যবহার করুন এবং সম্মান রেখে দ্বিমত করা, সাথে commitment দেখান। আমি প্রমাণ সহ আমার উদ্বেগ জানিয়েছি, তাঁর মতটা শুনেছি, আর আমরা একটা পথ বের করেছি। মূল সংকেতগুলো: আমি পেশাদারভাবে বিষয়টা তুলেছি, তথ্য দিয়ে সমর্থন করেছি, আর সিদ্ধান্ত হয়ে যাওয়ার পর পুরোপুরি সেটার পেছনে দাঁড়িয়েছি — কোনো মন খারাপ নয়।"

**এবার পুরোটা বুঝি (STAR নমুনা — নিজের মতো বদলে নিন):**

- **Situation:** "আমার manager একটা deadline ধরার জন্য automated test ছাড়াই একটা feature ship করতে চেয়েছিলেন।"
- **Task:** "আমার মনে হয়েছিল একটা core payments flow-এর জন্য ঝুঁকিটা অনেক বেশি। তাই গঠনমূলকভাবে বিষয়টা তোলা দরকার ছিল।"
- **Action:** "আমি নির্দিষ্ট ঝুঁকিটা ব্যাখ্যা করলাম — payments-এ একটা bug মানে আসল টাকা আর বিশ্বাস দুটোই হারানো। তারপর একটা মাঝামাঝি পথ প্রস্তাব করলাম: সময়মতো ship করব, কিন্তু শুধু critical payment path-গুলোতে test থাকবে। কম ঝুঁকির test পরে হবে। আমি দেখালাম এতে মাত্র ১ দিন বাড়বে।"
- **Result:** "আমরা মাঝামাঝি পথেই রাজি হলাম। Payment test-গুলো release-এর আগে একটা rounding bug ধরে ফেলল। পরে আমার manager আমাকে ধন্যবাদ দিয়েছিলেন এই দ্বিমতের জন্য।"

**পরামর্শ:**
- একটা **পেশাদার** দ্বিমত বাছুন (approach বা quality নিয়ে), ব্যক্তিগত ঝগড়া নয়।
- দেখান আপনি **শুনেছেন** এবং একটা **গঠনমূলক বিকল্প** দিয়েছেন, শুধু "না" বলেননি।
- আপনার কথা না টিকলে দেখান আপনি তবুও **সিদ্ধান্তের পেছনে দাঁড়িয়েছেন** এবং শেষে ভালোই হয়েছে (বা আপনি শিখেছেন)।

**Interviewer কেন জিজ্ঞেস করে:** এটা যাচাই করে আপনি সম্মান রেখে দ্বিমত করতে পারেন কি না, *এবং* team player হতে পারেন কি না — দুটোই গুরুত্বপূর্ণ।

**সাধারণ ভুল:** এমন গল্প যেখানে আপনি ঝগড়াটে ছিলেন। বা এমন গল্প যেখানে আপনি কোনো মেরুদণ্ড ছাড়াই মেনে নিয়েছেন — তাঁরা ভারসাম্য সহ দৃঢ়তা চান।

**যে Follow-up প্রশ্ন আসতে পারে:**
- *"তাঁরা যদি না বলতেন?"* → আমি ঝুঁকিটা পরিষ্কার করে জানাতাম (গুরুতর হলে লিখিতভাবে), তারপর সিদ্ধান্ত মেনে নিয়ে সমস্যাটার উপর নজর রাখতাম।

## <a id="q15"></a>15. এমন একটা সময়ের কথা বলুন যখন আপনি একটা app-এর performance ভালো করেছেন।

> Common · Medium · [🇬🇧 English](../software-engineer-flutter/section-22-leadership-behavioral.md#q15)

**সংক্ষিপ্ত উত্তর (এটাই বলুন):**
"STAR ব্যবহার করুন এবং একটা *মাপা* পদ্ধতি দেখান: আমি profiling দিয়ে সমস্যাটা চিহ্নিত করেছি, আসল কারণ খুঁজে বের করেছি, নির্দিষ্ট জায়গায় fix দিয়েছি, আর উন্নতিটা মেপেছি। সংকেতটা হলো — আমি অনুমান নয়, data দিয়ে optimize করি, আর Flutter-এর performance tool আমি জানি।"

**এবার পুরোটা বুঝি (STAR নমুনা — নিজের মতো বদলে নিন):**

- **Situation:** "একটা product list screen scroll করার সময় খুব বাজেভাবে jank করত — user-রা lag টের পাচ্ছিলেন।"
- **Task:** "এটা মসৃণ করার দায়িত্ব আমার ছিল (স্থির 60fps)।"
- **Action:** "আমি DevTools আর performance overlay দিয়ে profile করলাম। দেখলাম প্রতিবার scroll-এ পুরো list rebuild হচ্ছে, আর image cache হচ্ছে না। আমি `ListView.builder`-এ গেলাম, `const` আর `RepaintBoundary` যোগ করলাম, `cached_network_image` দিয়ে image cache করলাম, আর একটা ভারী filter হিসাব isolate দিয়ে UI thread থেকে সরালাম। আগে/পরে মাপটা আমি *release* mode-এ নিয়েছি।"
- **Result:** "Scrolling ~35fps আর চোখে পড়া jank থেকে মসৃণ 60fps-এ গেল। Frame build time 28ms থেকে 8ms-এর নিচে নামল।"

**পরামর্শ:**
- **আগে মাপুন** (profile), তারপর fix করুন, তারপর **আবার মাপুন** — **release** mode-এ।
- নির্দিষ্ট Flutter tool আর fix-এর নাম বলুন ([Q5 Performance](section-05-performance-bn.md#q1))।

**Interviewer কেন জিজ্ঞেস করে:** এটা data-driven পদ্ধতি আর সত্যিকারের Flutter performance জ্ঞান যাচাই করে।

**সাধারণ ভুল:** profiling ছাড়া অনুমান করে optimize করা। বা debug mode-এর সংখ্যা বলা (সবসময় release-এ মাপুন)।

**যে Follow-up প্রশ্ন আসতে পারে:**
- *"Bottleneck কীভাবে খুঁজে পেয়েছিলেন?"* → DevTools timeline, performance overlay, "Track Widget Rebuilds"।

**সম্পর্কিত:** [Q5 (Performance)](section-05-performance-bn.md#q1) · [Q11 — অর্জন](#q11)

## <a id="q16"></a>16. এমন একটা সময়ের কথা বলুন যখন একটা project ব্যর্থ হয়েছিল। আপনি কী শিখলেন?

> Very common · Medium–Hard · [🇬🇧 English](../software-engineer-flutter/section-22-leadership-behavioral.md#q16)

**সংক্ষিপ্ত উত্তর (এটাই বলুন):**
"STAR ব্যবহার করুন এবং একটা *সত্যিকারের* ব্যর্থতা বেছে নিন, যেখানে আপনি সৎভাবে দায় নিচ্ছেন আর স্পষ্ট শিক্ষা দেখাচ্ছেন। অন্যকে দোষ দেবেন না, নকল 'ব্যর্থতা'ও বাছবেন না। তাঁরা যে signal চান: আপনি ব্যর্থ হতে পারেন, দায় নিতে পারেন, শিখতে পারেন, আর শিক্ষাটা কাজে লাগাতে পারেন — senior-রা এভাবেই বড় হন।"

**এবার পুরোটা বুঝি (STAR নমুনা — নিজের মতো বদলে নিন):**

- **Situation:** "যথেষ্ট user validation ছাড়াই আমরা তাড়াহুড়ো করে একটা feature launch করেছিলাম।"
- **Task:** "আমি ছিলাম lead, আর দ্রুত ship করার জন্য চাপ দিয়েছিলাম।"
- **Action:** "৩ সপ্তাহে আমরা এটা বানিয়ে launch করলাম — কিন্তু adoption প্রায় শূন্য। আমি খুঁটিয়ে দেখলাম: user কী চায় সেটা যাচাই না করে আমরা ধরে নিয়েছিলাম। আমি user interview করলাম, দেখলাম আসল প্রয়োজন অন্যরকম, তারপর আমরা এটা নতুন করে বানালাম।"
- **Result:** "নতুন version-টা শক্তিশালী adoption পেল। শিক্ষা: বানানোর *আগে* user-দের দিয়ে assumption যাচাই করার উপর আমি এখন জোর দিই। এর পর থেকে এটা আমাদের আরও দুটো নষ্ট build থেকে বাঁচিয়েছে।"

**পরামর্শ:**
- **সত্যিকারের দায়** নিন ("আমি", "team আমাকে ডুবিয়েছে" নয়)।
- একটা **নির্দিষ্ট শিক্ষা** দেখান এবং পরে আপনি সেটা **কাজে লাগিয়েছেন** সেটাও দেখান।
- একটা **সত্যি কিন্তু সামলে নেওয়ার মতো** ব্যর্থতা বাছুন — মহাবিপর্যয়ও নয়, নকলও নয়।

**Interviewer কেন জিজ্ঞেস করে:** এটা বিনয়, আত্ম-সচেতনতা আর বেড়ে ওঠার ক্ষমতা যাচাই করে — যাঁরা "কখনো ব্যর্থ হন না" তাঁদের নিয়ে তাঁরা সন্দিহান।

**সাধারণ ভুল:** অন্যকে দোষ দেওয়া, ব্যর্থতা নয় এমন কিছু বাছা ("আমি খুব বেশি পরিশ্রম করি"), অথবা কোনো সত্যিকারের শিক্ষা না দেখানো।

**যে Follow-up প্রশ্ন আসতে পারে:**
- *"শিক্ষাটা আপনি কীভাবে কাজে লাগালেন?"* → পরের একটা নির্দিষ্ট উদাহরণ, যেখানে আপনি আরও ভালো করেছেন।

## <a id="q17"></a>17. Flutter আর Dart ecosystem-এর সাথে আপনি কীভাবে হালনাগাদ থাকেন?

> Common · Easy · [🇬🇧 English](../software-engineer-flutter/section-22-leadership-behavioral.md#q17)

**সংক্ষিপ্ত উত্তর (এটাই বলুন):**
"বিভিন্ন উৎস আর হাতে-কলমে চর্চার মিশ্রণ। আমি official Flutter/Dart channel আর release notes অনুসরণ করি, community পড়ি (newsletter, গুরুত্বপূর্ণ blog, conference talk), আর সবচেয়ে বড় কথা — side project-এ নতুন জিনিস *চেষ্টা* করে দেখি। আমার team আর code review থেকেও শিখি।"

**এবার পুরোটা বুঝি:**

**ধাপ ১ — Official উৎস।**
Flutter/Dart release notes আর official blog/YouTube — এতে আমি নতুন language feature (records, patterns), framework-এর পরিবর্তন (Impeller) আর deprecation সম্পর্কে জানি।

**ধাপ ২ — Community।**
একটা-দুটো newsletter (যেমন Flutter Weekly), সম্মানিত blog, conference talk (Flutter Forward/Engage), আর maintainer-দের অনুসরণ করা। এতে pattern আর ফাঁদগুলো সামনে আসে।

**ধাপ ৩ — হাতে-কলমে (সবচেয়ে গুরুত্বপূর্ণ)।**
শুধু পড়া যথেষ্ট নয় — আমি ছোট side project বা spike-এ নতুন feature চেষ্টা করি। এতে আমি সত্যিই বুঝি, শুধু নামগুলো চিনে রাখি না।

**ধাপ ৪ — Team থেকে শেখা।**
Code review, pairing আর team আলোচনা দুই দিকেই জ্ঞান ছড়ায়। কাউকে শেখানোও আমার নিজের শেখা পাকা করার একটা উপায়।

**Interviewer কেন জিজ্ঞেস করে:** Mobile খুব দ্রুত বদলায়; তাঁরা এমন কাউকে চান যিনি হালনাগাদ থাকেন, কিন্তু প্রতিটা চকচকে জিনিসের পেছনে ছোটেন না।

**সাধারণ ভুল:** নির্দিষ্ট কিছু ছাড়া গৎবাঁধা "আমি blog পড়ি", অথবা চেষ্টা না করেই নতুন জিনিস জানার দাবি করা।

**যে Follow-up প্রশ্ন আসতে পারে:**
- *"সাম্প্রতিক কোন Flutter/Dart পরিবর্তন আপনার পছন্দ?"* → একটা নির্দিষ্ট, সাম্প্রতিক উদাহরণ তৈরি রাখুন (যেমন Dart 3 records/patterns, Impeller)।

## <a id="q18"></a>18. এই Senior Flutter role-টা আপনি কেন চান?

> Common · Easy–Medium · [🇬🇧 English](../software-engineer-flutter/section-22-leadership-behavioral.md#q18)

**সংক্ষিপ্ত উত্তর (এটাই বলুন):**
"*তাঁদের* নির্দিষ্ট বিষয়গুলোকে *আপনার* লক্ষ্যের সাথে জুড়ুন। দেখান যে আপনি কোম্পানি/product নিয়ে পড়াশোনা করেছেন, সত্যিই কোন জিনিসটা আপনাকে টানছে সেটার নাম বলুন, আর সেটাকে আপনার বেড়ে ওঠার পথের সাথে মেলান। যেকোনো কোম্পানিতে খাটে এমন গৎবাঁধা উত্তর এড়িয়ে চলুন — নির্দিষ্ট হোন।"

**এবার পুরোটা বুঝি:**

**ধাপ ১ — আগে থেকে পড়ে যান।**
তাঁদের product, tech আর চ্যালেঞ্জ জেনে যান। নির্দিষ্ট কিছুর উল্লেখ করুন: "আপনাদের app [users]-দের সেবা দেয়, আর [আপনি দেখেছেন এমন একটা আসল চ্যালেঞ্জ/feature] নিয়ে আমি উৎসাহিত।"

**ধাপ ২ — নিজের শক্তি আর লক্ষ্যের সাথে জুড়ুন।**
দুই দিকের মিল দেখান: আপনি কী নিয়ে আসছেন (senior Flutter, leadership, সংশ্লিষ্ট domain) *এবং* আপনি কোন দিকে বড় হতে চান (আরও ownership, scale, mentoring)।

**ধাপ ৩ — সত্যিকারের আগ্রহ দেখান।**
হয়তো product-এর mission, tech-এর চ্যালেঞ্জ, team-এর সুনাম, বা remote culture। আসল উৎসাহ আলাদা করে চোখে পড়ে।

**ধাপ ৪ — কথাটা শুধু নিজেকে নিয়ে নয়, তাঁদের নিয়েও রাখুন।**
"আমি কী পাব" আর "আমি কী দেব" — দুটোর মধ্যে ভারসাম্য রাখুন। Senior candidate-রা দেখান যে তাঁরা value যোগ করবেন, শুধু বেতন নেবেন না।

**Interviewer কেন জিজ্ঞেস করে:** এটা যাচাই করে আপনি সত্যিই *তাঁদের* নিয়ে আগ্রহী, নাকি যেকোনো একটা চাকরি দরকার — আর আপনি থাকবেন কি না।

**সাধারণ ভুল:** গৎবাঁধা উত্তর ("ভালো কোম্পানি, ভালো tech") যেটা যেকোনো জায়গায় খাটে, অথবা শুধু salary/perks নিয়ে কথা বলা।

**যে Follow-up প্রশ্ন আসতে পারে:**
- *"আমাদের product সম্পর্কে আপনি কী জানেন?"* → নির্দিষ্ট তথ্য তৈরি রাখুন — এটাই আসল আগ্রহ প্রমাণ করে।

## <a id="q19"></a>19. ৩–৫ বছর পরে নিজেকে কোথায় দেখেন?

> Common · Easy · [🇬🇧 English](../software-engineer-flutter/section-22-leadership-behavioral.md#q19)

**সংক্ষিপ্ত উত্তর (এটাই বলুন):**
"এমন উচ্চাকাঙ্ক্ষা দেখান যেটা বাস্তবসম্মত বেড়ে ওঠার পথে মেলে আর role-এর সাথে মেলে — senior/staff বা tech lead হিসেবে গভীরে যাওয়া, বড় system আর বেশি mentoring নেওয়া। সৎ থাকুন, আর তাঁদের মতো একটা কোম্পানির *সাথে* বড় হওয়ার কথা বলুন। 'এক বছরে নিজের কোম্পানি খুলব' নয়।"

**এবার পুরোটা বুঝি:**

**ধাপ ১ — বাস্তবসম্মত একটা দিক দেখান।**
সৎ ও প্রচলিত পথ: গভীর technical দক্ষতা (staff/principal), অথবা technical leadership (tech lead/architect)। আপনার জন্য যেটা সত্যি, সেটাই বাছুন।

**ধাপ ২ — Role-এর সাথে জুড়ুন।**
"আমি tech-lead role-এ বড় হতে চাই — architecture-এর ownership আর mentoring নিয়ে। এই কারণেই এমন scope-এর একটা senior role আমাকে টানে।" দেখান যে আপনি তাঁদের *সাথে* বড় হবেন।

**ধাপ ৩ — সৎ থাকুন, কিন্তু employer-বান্ধবভাবে।**
"এক বছরে চলে যাব" বা "আপনার interviewer-এর চাকরিটা আমি চাই" — এসব বলবেন না। এমন উচ্চাকাঙ্ক্ষা দেখান যেটা কোম্পানি সমর্থন করতে পারে আর যেটা থেকে তারা লাভবান হয়।

**ধাপ ৪ — Impact আর শেখার উপর জোর দিন।**
বেড়ে ওঠাকে শুধু পদবি নয়, বড় impact আর দক্ষতা দিয়ে বোঝান: "বড় project-এর নেতৃত্ব দেওয়া, বেশি mentoring করা, আর কঠিন system-design সমস্যা সামলানো।"

**Interviewer কেন জিজ্ঞেস করে:** এটা উচ্চাকাঙ্ক্ষা, আত্ম-সচেতনতা আর আপনার লক্ষ্য তাঁদের দেওয়ার সামর্থ্যের সাথে মেলে কি না — সেটা যাচাই করে (retention)।

**সাধারণ ভুল:** কোনো দিক না থাকা ("আমি জানি না"), অবাস্তব লাফ, অথবা শীঘ্রই চলে যাওয়ার ইঙ্গিত দেওয়া।

**যে Follow-up প্রশ্ন আসতে পারে:**
- *"Management নাকি technical track?"* → সৎ থাকুন; দুটোই ঠিক আছে, শুধু দেখান যে আপনি এটা নিয়ে ভেবেছেন।

**সম্পর্কিত:** [Q18 — এই role কেন](#q18) · [Q17 — হালনাগাদ থাকা](#q17)

## <a id="q20"></a>20. আপনার সবচেয়ে বড় technical দুর্বলতা কী?

> Very common · Medium · [🇬🇧 English](../software-engineer-flutter/section-22-leadership-behavioral.md#q20)

**সংক্ষিপ্ত উত্তর (এটাই বলুন):**
"একটা *সত্যিকারের* দুর্বলতার নাম বলুন, তারপর দেখান সেটা নিয়ে আপনি এখন কী করছেন। কৌশলটা কোনো শক্তিকে দুর্বলতার মোড়কে সাজানো নয় ('আমি perfectionist') — interviewer-রা এটা ধরে ফেলেন। এমন কিছু বাছুন যেটা সত্যি, কিন্তু role-এর মূল অংশ নয়। আর নির্দিষ্ট উন্নতি দেখান।"

**এবার পুরোটা বুঝি:**

**ধাপ ১ — সত্যি ও সৎ একটা দুর্বলতা বাছুন।**
এমন কিছু যেটা সত্যি, কিন্তু role-এর জন্য deal-breaker নয়। উদাহরণ: "career-এর শুরুর দিকে আমি test লেখায় কম সময় দিতাম" বা "requirement পুরোপুরি পরিষ্কার করার আগেই আমি code-এ ঝাঁপিয়ে পড়তাম।"

**ধাপ ২ — আত্ম-সচেতনতা আর পদক্ষেপ দেখান।**
আসল signal হলো *বেড়ে ওঠা*: "আমি খেয়াল করলাম এতে rework হচ্ছে। তাই এখন আমি সবসময় acceptance criteria লিখে রাখি আর code করার আগে PO-র সাথে নিশ্চিত হই — এটা দুইবার ভুল জিনিস বানানো থেকে আমাকে বাঁচিয়েছে।"

**ধাপ ৩ — ভান করবেন না।**
"আমি perfectionist / আমি খুব বেশি পরিশ্রম করি" একটা গৎবাঁধা কথা। এতে বোঝা যায় আপনি প্রশ্নটা এড়িয়ে যাচ্ছেন। সত্যিকারের সততা (সাথে উন্নতি) বেশি আস্থা তৈরি করে।

**ধাপ ৪ — Role-এর সাথে মানানসই রাখুন।**
কাজের মূল অংশ এমন কোনো দুর্বলতার নাম বলবেন না (যেমন Flutter role-এ "আমি Flutter-এ দুর্বল")। পাশের কোনো জিনিস বাছুন, যেটা উন্নত করা সম্ভব।

**Interviewer কেন জিজ্ঞেস করে:** এটা আত্ম-সচেতনতা আর সততা যাচাই করে — আর আপনি নিজের বেড়ে ওঠা নিয়ে সক্রিয়ভাবে কাজ করেন কি না।

**সাধারণ ভুল:** নকল "humblebrag" দুর্বলতা, অথবা সত্যিকারের দুর্বলতা কিন্তু উন্নতির কোনো প্রমাণ নেই।

**যে Follow-up প্রশ্ন আসতে পারে:**
- *"এটা আপনি কীভাবে উন্নত করছেন?"* → একটা নির্দিষ্ট, বাস্তব পদক্ষেপ আর তার ফলাফল তৈরি রাখুন।

**সম্পর্কিত:** [Q16 — একটা ব্যর্থতা](#q16) · [Q2 — mentoring (growth mindset)](#q2)

# <a id="cheatsheet"></a>Cheat Sheet (শেষ রাতের রিভিশন)

Interview-এর দিন সকালে এটা পড়ুন। STAR template, table, তারপর মনে রাখার কথা।

## STAR template (নিজের গল্পগুলো বসান)

```
Situation:  (1–2 sentences of context)
Task:       (your specific goal)
Action:     (what I did — the longest part, use "I")
Result:     (the outcome WITH numbers)
```

## যে গল্পগুলো তৈরি রাখবেন (৩–৪টি নমনীয় গল্প)

| গল্প | যে প্রশ্নগুলো ঢাকে |
|---|---|
| আপনি নেতৃত্ব দিয়েছেন এমন একটা project | [Q11](#q11), [Q12](#q12) |
| আপনি ঠিক করেছেন এমন একটা production bug | [Q13](#q13) |
| ভালোভাবে সামলানো একটা দ্বিমত | [Q3](#q3), [Q14](#q14) |
| একটা ব্যর্থতা + শিক্ষা | [Q16](#q16), [Q20](#q20) |
| একটা performance জয় | [Q11](#q11), [Q15](#q15) |

## Leadership — এক লাইনে প্রতিটি

| বিষয় | Senior উত্তর |
|---|---|
| Code review | আগে correctness; প্রশ্ন করুন, ভদ্র থাকুন |
| দ্বিমত | ego নয়, প্রমাণ; disagree and commit |
| নতুন tech | আসল সমস্যা + spike + buy-in, hype নয় |
| Tech debt | দৃশ্যমান করুন, প্রতি sprint-এ budget রাখুন |
| গতি বনাম মান | সচেতন, নথিভুক্ত trade-off |
| Architecture | প্রয়োজনের সাথে মানানসই; ADR দিয়ে document করুন |

## এক লাইনের মনে রাখার কথা

- প্রতিটা behavioral উত্তর **STAR** দিয়ে দিন; **শেষ করুন সংখ্যা দিয়ে**। (section-এর শুরুতে)
- **"আমি"** বলুন, "আমরা" নয় — তাঁরা *আপনাকে* hire করছেন। ([Q11](#q11))
- **Disagree and commit** — প্রমাণ দিয়ে আপত্তি জানান, তারপর সিদ্ধান্তটাকে সমর্থন করুন। ([Q3](#q3), [Q14](#q14))
- **Production bug**: আগে আটকান, তারপর root-cause বের করুন, একটা test দিয়ে ঠেকান। ([Q13](#q13))
- **Failure**: সৎভাবে দায় নিন, শিক্ষাটা দেখান আর সেটা কীভাবে কাজে লাগিয়েছেন তাও দেখান। ([Q16](#q16))
- **Weakness**: সত্যিকারের একটা দুর্বলতা + বাস্তব উন্নতি; কখনোই নকল humblebrag নয়। ([Q20](#q20))
- **এই role কেন / ৩–৫ বছর**: *তাঁদের* জন্য নির্দিষ্ট করে বলুন, বাস্তবসম্মত growth দেখান। ([Q18](#q18), [Q19](#q19))
- **Mentoring/onboarding**: *কেন* সেটা শেখান, স্বনির্ভরতা গড়ুন, আগে ছোট জয়। ([Q2](#q2), [Q8](#q8))
- **গতি vs মান**: সচেতনভাবে সিদ্ধান্ত নিন, debt লিখে রাখুন, জানিয়ে দিন। ([Q6](#q6))

# অনুশীলন: interviewer-রা কীভাবে আরও গভীরে যান

Behavioral interview নির্দিষ্ট তথ্যের জন্য খুঁড়তে থাকে। মুখে বলে বলে অনুশীলন করুন:

1. *"একটা কঠিন bug-এর কথা বলুন।"* → STAR; আগে আটকান, root-cause বের করুন, ঠেকানোর জন্য test, blameless post-mortem।
2. *"আপনার নিজের অংশটা কী ছিল?"* ('আমরা' বলা উত্তরের পরে) → "আমি"-তে যান আর আপনার নির্দিষ্ট কাজগুলোর নাম বলুন।
3. *"ফলাফল কী হলো?"* → সবসময় সংখ্যা রাখুন (crash rate, fps, adoption, বাঁচানো সময়)।
4. *"আবার করলে কী আলাদা করতেন?"* → নিজেকে যাচাই করার ক্ষমতা দেখান — একটা সৎ উন্নতি।
5. *"অন্যদের বদলে আপনাকে কেন নেব?"* → আপনার নির্দিষ্ট শক্তিগুলো তাঁদের নির্দিষ্ট প্রয়োজনের সাথে মিলিয়ে দিন।

পরিষ্কার গল্প, সৎভাবে দায় নেওয়া, আর সংখ্যা — শান্তভাবে বলা হলে — ঠিক এটাই সেই senior signal যা interviewer-রা চান, remote আর BD দুই ধরনের interview-তেই।
